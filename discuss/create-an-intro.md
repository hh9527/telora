# 如何介绍 Telora

- Stage: Discussion
- Scope: Telora introduction narrative, evidence, and application examples
- Primary example: `discuss/gcc-wrapper.md`

## 目的

这份讨论稿记录 Telora 介绍文档的写作路线。目标不是把 README 扩写成特性
清单，而是让第一次接触 Telora 的读者理解：它解决什么问题、为什么没有直接
选择已有配置格式或通用语言，以及它如何把封闭的数据计算投射到真实应用。

介绍应当从问题域出发，用一个足够具体的应用贯穿设计理念。语言特性只有在
回应问题时才出现，尚未实现的能力必须与当前事实分开。

## 叙事主线

介绍可以分为三个连续层次。

### 1. 从可编程配置到可信计划

起点是可编程配置，但问题并不止于“让配置支持函数”。真实系统需要完成：

```text
外部数据
  -> 结构化表达
  -> 类型化与验证
  -> 确定转换
  -> 来源明确的诊断
  -> 面向应用的具体计划
```

应用投射可以包括 build rule、增强型 dotslash、Helm chart，以及 agentic plan
IR。它们共同需要的不是某一种文件格式，而是一个封闭、纯粹、有界、可组合的
计算世界，以及少量显式的内外连接点。

### 2. 现有方案为何没有完全覆盖这个位置

prior art 应当客观描述理念差异，不以语法细节制造优劣。

#### 数据表达类

这一类方案始终以数据为中心，可以按附加能力分成三层。

第一层是纯数据表达。JSON 提供了一个成功而清楚的边界：文件描述树状数据，
解析结果可以被几乎所有语言和工具消费。它适合交换、缓存和检查最终结果；
读者也不需要先理解一套求值模型。YAML、TOML 和 KDL 改善了不同场景下的人工
书写和结构表达，但仍然首先定义数据表示。

但 JSON 本身不表达复用、条件选择、领域类型、验证或转换。需求增长以后，
这些逻辑通常进入模板、schema 工具、生成器或外围脚本。最终数据依然简单，
生成它的路径却分散到多个系统，错误也可能只能指向生成后的 JSON，而不能
同时解释原始输入与拒绝它的规则。

第二层在数据之上增加校验。JSON Schema 能描述结构、字段、取值范围和组合
约束，并让编辑器、CI 与不同语言共享一份契约。它解决的是“这个值是否符合
描述”，而不是“怎样通过可复用计算得到这个值”。复杂的跨字段转换、依赖
选择和应用计划仍然需要另一个执行层。

第三层加入面向数据的动态处理。`JSON + jq/jaq` 让 JSON 获得强大的查询、
过滤、组合和流式转换能力；对于一次性数据处理，它往往比引入通用脚本语言
更直接。这里的“面向数据”不是指计算必然终止：jq 提供递归，不能把它描述成
计算意义上的有限语言。它的边界是操作对象和编程模型主要围绕 JSON filter。

问题不在于 jq/jaq 缺少表达力，而在于应用规模扩大以后还需要在它之外组合
其他契约：schema 或宿主代码负责领域类型与输入验证，包管理和调用脚本负责
依赖及执行环境，错误通常围绕当前 filter 和当前 JSON 值展开，而不是统一保留
“外部数据来源、验证规则位置、生成步骤和最终 Host 协议”之间的关系。

因此 JSON + jq 可以很好地回答“怎样得到另一个 JSON”，但当目标上升为“怎样
从锁定依赖和 Host 输入得到一个类型化、可诊断、可授权的应用计划”时，系统
边界会重新分散。Telora 希望保留 jq 式数据转换的直接性，同时把类型、模块、
provenance/blame、有界求值和结果协议放进同一个程序模型。

#### GPL 通用语言类

通用语言把重点从数据格式转向开放计算，但静态保证和运行时边界存在几个
不同层次。

Python 和 JavaScript 代表开放的动态运行时。它们可以读取环境、访问网络、
调用系统 API，并使用成熟生态解决几乎任意应用问题。代价是配置或计划程序
能够观察和影响的世界很大；依赖、确定性、资源上界、缓存和 dry-run 语义需要
由应用框架重新建立。

Python type annotation 和 TypeScript 在这一模型上增加渐进式静态检查。它们能
在执行前发现大量接口错误，又允许未标注代码、动态值、断言和外部边界逃逸
静态模型。这不是缺陷意义上的“不完备诊断”，而是有意选择的兼容性边界：
类型检查提供广泛但非证明级的保证，运行时与效果模型仍然保持开放。

Scheme 展示的是另一种开放性。它的经典判断是“代码也是数据”：极小核心、
同像表示、宏和灵活的元编程让用户能够塑造自己的语言。这带来很大的抽象和
扩展空间，但也扩大了静态推理边界。程序可以制造或变换随后执行的代码时，
名称绑定、控制流、调用关系和终止性不再只由原始程序文本决定；类型检查、
增量分析、缓存和来源解释都需要理解展开或求值后的代码。具体 Scheme 实现
可以施加纪律，但这些保证不是“代码也是数据”本身自然提供的。

Coq、Agda、Idris 等证明导向语言位于另一端。依赖类型、全函数片段和证明检查
可以把强性质写入程序，并由可信内核或类型检查器验证。强保证来自对程序、
终止性和效果边界施加纪律，而不是“开放动态能力再加完整诊断”。此外，Coq、
Agda 与 Idris 的执行和可信边界并不完全相同，介绍只需把它们作为证明导向
路线的代表，不应声称任意程序性质都能自动证明。

这些 GPL 路线各自覆盖了 Telora 所需能力的超集或更强理论基础，但也把问题带
到更大的运行时、效果系统或证明工程中。Telora 不追求通用计算或通用定理证明；
它选择一个更窄的封闭数据计算世界，以较低使用成本提供足够的类型、诊断和
Host 边界保证。

#### DSL 领域语言类

CUE、KCL 和 Nickel 直接面对可编程配置、约束、合并和验证问题，比由数据格式
和外围脚本组成的方案更接近 Telora 的生态位。它们已经证明配置计算值得拥有
独立语言模型，也各自选择了不同的约束、类型、契约和求值语义。Telora 与它们
的差异不应表述为“支持更多语法”，而应落在设计重心：普通不可变函数、显式
模块、类型对象与用户态 interpreter、结构化 provenance/blame，以及把最终值
交给不同 Host adapter 的统一边界。

这里所说的 DSL“魔法”不是贬义，而是指只有语言实现才能赋予意义的专用规则：
例如约束合一、schema 检查、契约应用、字段合并与冲突消解。CUE、KCL 和 Nickel
用这些核心语义换取了各自领域内非常直接的表达。代价是每增加一类能力，用户
和工具都可能需要理解另一套专用组合、错误传播和来源规则。

Telora 的核心判断是：类型不应只在检查器内部存在，它同时是程序可以传递和
观察的元数据值。一个 `TypeOf(A)` 把运行时类型描述与静态的 `A` 联系起来，
因此同一份类型定义可以贯穿：

```text
数据表示
  -> parse / decode
  -> 类型与领域约束
  -> 普通函数转换
  -> display / encode
  -> Host protocol
```

parse、codec、display 或用户态 interpreter 不需要各自发明一套隐藏 schema、
派生机制和特殊调用规则。它们接收显式类型对象或由类型对象携带的声明性
元数据，最终产生普通的类型化函数和值。用户仍然沿着模块 import、函数调用和
数据流理解程序，而不是学习多层编译期魔法。

这也是 Telora 对 DSL 竞争力的主张：更统一、容易解释的模型不意味着牺牲抽象
能力。类型导向的能力可以作为普通函数传递，策略可以在模块间复用，同一个
领域类型可以连接输入、约束、转换和输出；provenance/blame 又能解释数据来自
哪里、哪条规则拒绝了它。Telora 希望在抽象能力、可复用度和可解释性上不弱于
专用配置 DSL，同时保持较少的特殊概念。GCC wrapper 将作为这项主张的实际
验收，而不是只用小型语法示例证明它。

Telora 在这里继承了部分 Scheme 基因，但选择了更窄的反射边界：不是“代码也
是数据”，而是“类型也是数据”。程序可以检查类型描述，并用普通递归函数解释
它；程序不能 quote、改写再执行任意 Telora 代码。需要把擦除的元数据解释器
恢复为静态类型化能力时，使用受控的 contextual intrinsic：

```telora
def my_show: for(A) Fn(TypeOf(A)) -> Fn(A) -> Result(String, BlameError)
    = interpreter!(show_dyn);
```

`interpreter!` 看起来像宏，但不开放宏系统、代码生成或运行时 `eval`。它只在
一个可检查的高阶签名与一个显式的 Dyn/TypeDesc 解释器之间建立系统验证的
桥梁。解释算法仍由普通 Telora 代码定义，调用者得到的仍是普通类型化函数。

这个限制大幅缩小了静态推理问题：编译器不需要证明任意生成代码的绑定与
类型，只需验证有限的 adapter 契约；模块依赖和可执行函数集合在求值前仍然
确定。Telora 因而尽量保留类型检查、可分析性、有界求值和来源解释，同时保有
编写通用数据 interpreter 的能力。

这里的“通用”主要与配置 DSL 的专用机制对照：同一个“类型也是数据 + 普通
函数 + `interpreter!`”模型，应当能够实现可复用的 parse、codec、validate、
display、Eq/Hash 等类型导向能力，而不必为每一项能力增加新的语言内建派生或
约束系统。它不表示 Telora 拥有 Scheme 式任意语言扩展或 Coq 式通用定理证明。
Telora 是否真正不弱于其他 DSL，需要由跨模块复用、嵌套类型、来源诊断和 GCC
wrapper 这类应用级案例持续验证。

介绍不需要声称 Telora 全面替代这些项目。更准确的说法是：Telora 探索从数据
表达、验证和转换出发，生成可审查应用计划的另一种组合方式。

### 3. Telora 的回应

核心理念可以概括为：

- 纯封闭的世界承载所有确定计算；
- 模块路径和依赖在求值前确定，不提供运行时 `eval`；
- 类型同时是可传递的元数据；解析、codec、display 和用户态 interpreter 在
  这一个模型上组合；
- 失败保留数据来源与规则位置，不把诊断降格为一段字符串；
- fuel、栈、调用深度和分配配额为 Host 提供有界求值；
- Host 只通过轻量连接点提供输入，并消费完整、类型化的结果计划。

这里的“纯”不是拒绝真实应用，而是把效果推迟到计划已经计算、检查和展示
之后。Telora 程序描述确定内容，Host 决定是否下载、写文件或启动进程。

## 贯穿案例：GCC wrapper

`discuss/gcc-wrapper.md` 是介绍文档的主要思想实验。需求来自真实工具链分发：

1. 一个入口同时使用 Host 相关的 GCC 和 TARGET 相关的 sysroot；
2. gcc、g++、ar 复用相同工具链定义和安装结果；
3. wrapper 根据 TARGET 选择 sysroot，并改写命令行；
4. wrapper 自动加入确定性的 file/debug prefix map；
5. 配置、环境变量或最终计划错误必须能够被诊断；
6. dry-run 在任何效果发生前给出完整 `ExecEnv`。

最终入口应当短到能够直接说明架构：

```telora
#!/usr/bin/env -S telora exec --dry-run --

option "crate.dependency" {
    name: "gcc-toolchain-define",
    source: 'GithubRepo({
        repo: "hh9527/gcc-toolchain-define",
        rev: "0123456789abcdef",
    }),
};
option "crate.dependency" {
    name: "gcc-wrapper",
    source: 'GithubRepo({
        repo: "hh9527/gcc-wrapper.telora",
        rev: "0123456789abcdef",
    }),
};

import "std/rt-types/exec" { ExecFn };
import "gcc-toolchain-define/source.json" as source;
import "gcc-wrapper/toolchain" { wrap_gcc };

export def exec: ExecFn = wrap_gcc(source);
```

这段代码同时呈现三类输入：

- `std/rt-types/exec.telora` 是公开的 Host 边界协议；
- `source.json` 是锁定依赖提供的原始外部数据；
- `wrap_gcc` 是普通 Telora 模块提供的纯验证与转换函数。

`ExecFn` 本身不授予效果权限。用户选择 `telora exec`，Host 才会注入请求、读取
`exec` 导出、校验 `ExecEnv` 并执行或展示计划。协议是普通数据类型，效果由
运行模式决定。

数据链路因此非常具体：

```text
source.json
  -> decode 与领域验证
  -> 类型化 toolchain definition
  -> Host/TARGET 选择
  -> argv rewrite
  -> ExecEnv
  -> dry-run / Host authorization / effects
```

错误的工具链数据应指向 `source.json`；错误的转换规则应指向 wrapper 模块；
不符合执行协议的结果由 Host adapter 拒绝。这个例子把 Telora 的数据输入、
类型化、转换、诊断和应用投射放进了同一条路径。

## 从案例投射到其他领域

GCC wrapper 不是一个孤立 demo。替换输入和最终协议以后，同一个模型可以表达：

- build rule：输出 artifact DAG 或 `OutputPlan`；
- Helm chart：输出经过 schema 和来源验证的 Kubernetes 对象；
- agentic plan IR：把模型产生的意图转换成 Host 可授权的确定计划；
- 数据转换工具：读取 JSON/TOML/YAML，验证后输出结构化或格式化文本。

介绍应强调这些场景共享的边界，而不是暗示 Telora 已经内置每个领域的框架。

## 当前证据与诚实边界

思想实验既是写作素材，也是实现探针。目前已经能够表达多个安装动作、平台
选择、hash 安装位置、字符串插值、数组组合和 typed `ExecEnv`，单文件
`telora exec --dry-run` 也已有可执行证据。

但完整案例尚未成立：RFC 0158 已验证跨模块高阶闭包和缩减的 `ExecFn` 形状，
顶层静态 `option`、GitHub dependency provider、稳定的 runtime protocol 模块、
Dict 安全读取和成熟 argv rewrite API 仍需推进。

介绍文档必须区分：

1. 今天已经实现并经过测试的能力；
2. 可以通过当前语法检查、但被实现缺口阻挡的组合；
3. 用于约束路线图的目标代码。

不能用概念上的可表达性替代端到端证据，也不应为了让示例看起来完整而复制
共享逻辑、隐藏运行时错误或假装外部效果已经实现。

## 写作原则

1. 先讲问题，再讲设计回应，最后才给能力名称。
2. 用 GCC wrapper 贯穿全文，而不是堆叠互不相关的小例子。
3. 比较 prior art 时描述边界和理念差，不争论无关紧要的表面语法。
4. 代码优先展示普通数据、普通函数和显式模块，不制造专用 DSL 的错觉。
5. 把 closed world 与 Host connection point 同时讲清，避免把 Telora 描述成只能
   计算静态常量的语言。
6. README.md 与 README.zh.md 保持相同事实、结构和承诺；英文版基于稳定后的
   中文叙事更新。
7. 所有能力主张都应有当前实现、测试或明确标注的路线图作为依据。

## 下一步

先按 GCC wrapper 思想实验推进对应伞 RFC。当目标入口能够端到端 dry-run 后，
再以本讨论稿为提纲改写正式 introduction。这样介绍文档讲述的是已经被真实
应用验证的设计，而不是孤立功能的愿望清单。
