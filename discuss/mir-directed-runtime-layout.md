# 利用已闭合 MIR 设计运行时数据布局

- 阶段：讨论
- 日期：2026-09-11
- 后续：方案确定后再形成 RFC

本文记录对下一阶段运行时的设想，不代表现有实现已经采用这些布局，也不承诺立即更换执行后端。

## 出发点

SealedMir 已经确定类型、符号引用和泛型实例。后续 codegen 应机械地消费这些结果，运行时不再重新猜测类型。下一步可以让这些静态信息进一步决定值表示、字段偏移、数组步长和调用约定。

目标不局限于减少字节码 VM 的开销，也应为 Cranelift 或 Wasm 后端提供共同基础。Cranelift 是机器码生成器，Wasm 是执行目标，两者不是同一层的互斥选择。现阶段先讨论共同的数据表示，不决定后端优先级。

基本关系可以是：

```text
SealedMir + 目标布局规则
          ↓
LayoutTable：TypeId → 大小、对齐、字段偏移、分支布局
          ↓
执行 IR / codegen
          ↓
字节码 VM、native 或 Wasm
```

TypeId 表达类型身份；物理布局属于目标对应的布局表。稳定 ID 不意味着跨源码修订的持久身份。

## 一、允许不同类型具有不同值宽

不要求所有值都通过一个同宽、携带类型标签的通用 Val 表示。静态类型已知的位置无需重复保存 TypeId；dyn 或未来的 trait object 才需要动态身份信息。

这里的“多值宽”是不同类型具有不同的固定宽度，不意味着数组中每个元素都具有不确定的长度。Array(T) 的元素步长仍由 T 的布局决定。

暂定以 64 位 word 作为执行槽位单位，但布局计算以字节大小和对齐为基础，最后才向 word 取整。

| 类型 | 初步槽位宽度 | 数据表示方向 |
| --- | --- | --- |
| Int / Float / Bool | 1 word | 标量位模式 |
| String | 2 words | inline 内容，或 arena 引用与范围、标志 |
| Array | 2 words | HeapId、start、end 各为 u32 |
| Record | 1 word | 指向固定布局对象的 HeapId |
| Dict | 1 word | 指向字典对象的 HeapId |
| 无 payload enum | 1 word | 分支 tag |
| 有 payload enum | 常见情况为 2 words | tag 加原始 payload；一般规则见后文 |

Record 的引用只占一个 word，不意味着对象字段同宽。对象内部按各字段布局确定偏移；Dict 保留动态键查找语义。Tuple 的内联或间接存储方式尚需确定。

## 二、arena 引用采用 HeapId

上述 ptr 是逻辑上的 arena 引用，不必是宿主机器指针。初步考虑 HeapId 使用 u32。

Array 的实际描述因此只需要 12 字节：

```text
HeapId: u32
start:  u32
end:    u32
```

独立进入 word 槽位时占 16 字节，末尾 4 字节为 padding。slice 复用同一个底层存储，只改变范围，不复制元素。元素的数据与来源使用相同的底层范围。

HeapId 的 u32 范围限制的是可寻址的身份空间；具体限制取决于它是对象索引、偏移还是其他句柄，不能直接等同于 4 GiB 堆上限。start/end 为 u32 则明确约束可表示的数组范围。

MainWorld 与 WorkWorld 如何区分引用、如何查找对象，以及初始化发布时是否需要重写 HeapId，仍属于待定的内存模型。稳定的 TypeId 不等于对象引用也自动跨 world 稳定。

## 三、来源是必须保留的冷数据

来源至少包括当前指令位置，以及值或字段的原始来源。仅保存指令位置不足以支持值经过函数传递后的准确诊断。

暂以三个 u32 表达一个位置项，具体字段语义沿用或另行明确现有来源模型：

```rust
values: Vec<u64>,
locs: Vec<[u32; 3]>,
```

正常计算主要读取 values；来源内容一般在出错时读取。分列的核心收益是读局部性：热路径不把来源信息一起带入缓存，减少缓存占用和内存带宽消耗。

来源传播仍然必须正确维护。复制或构造值可能需要写入来源，不能把“低概率读取”理解为“可以丢弃来源”。是否进一步使用 OriginId 压缩是独立议题，本轮不以来源链追溯替代明确的位置保存。

### 按 word 下标对齐

为了避免逻辑值索引与物理 word 偏移之间的额外映射，接受多 word 值占用多个 loc item：

```text
values: [scalar, array_word_0, array_word_1, next_scalar]
locs:   [loc_0,  array_loc,    unused,       loc_2]
```

对于只有一个整体来源的值，使用首 word 对应的位置，附加槽位可不承载有效来源。这样同一个 word 偏移即可定位数据和来源，无需第二套运行时索引表。

这会增加冷列的空间占用，也可能增加分配和写入成本；收益是寻址与 codegen 简单，并保持热列紧凑。冷数据仍然占内存，不能把它视为零成本。

包含多个独立字段来源的对象，需要保留各字段的来源。尤其当多个 u32 字段共享一个 word 时，不能假设一个 loc item 能表示任意数量的独立来源。对象内部来源布局需明确；本轮不通过任意子 word 字段压缩牺牲诊断精度。

## 四、dyn / trait object 优先不额外装箱

倾向于直接携带动态类型身份与 payload，而不是仅为了类型擦除再分配一层包装对象。

具体类型原本已经间接存储时，沿用原 HeapId；标量可直接存储。动态类型标签与 payload 放在一起，不为所有普通值维护一整列 type_ids。动态分派和类型判断可能频繁读取标签，它不像来源那样天然属于冷数据。

例如 TypeId 为 u32、Array 布局对齐为 4 字节时：

```text
[TypeId:u32][HeapId:u32][start:u32][end:u32]
```

两 word 即可容纳，无需复制数组内容或额外装箱。

这不等于所有类型都能直接放进固定两 word 的 dyn。一般 dyn 需要统一的容器宽度，并明确超过内联容量的 payload 如何间接存储；该容量、对齐及转换规则尚未决定。trait 分派使用 TypeId 查询实现表，还是额外携带实现表身份，也尚未决定。

## 五、enum 的布局与普通聚合布局一致

无 payload 的 enum 只需一个 word。带 payload 的 enum，常见目标是 tag 加 payload 共两 word，但不为这个目标引入特殊的组合编码。

Array 是一个直接例子：

```text
[tag:u32][HeapId:u32][start:u32][end:u32]
```

tag 与 12 字节 Array 合计 16 字节。因此不能先把 Array 向两个 word 取整，再机械增加一个 tag word。

一般布局需要考虑 tag、payload 对齐、最大分支大小和最终对齐。同一个 enum 类型具有统一宽度，未激活分支的数据不读取。如果 payload 更大，就增加整体宽度或引入明确的间接存储；递归路径必须通过间接存储得到有限布局。

两 word 不是所有带 payload enum 的硬性保证。大分支是否间接存储，需要权衡数组步长膨胀与间接访问成本。

## 六、限制 pack/unpack 的复杂度

核心原则：一个具体类型只有一种数据表示，进入 enum 或 dyn 后不为它重新设计编码。

例如 Array 始终是同样的三个 u32。独立存放时有外部 padding；嵌入 variant 时按外层布局计算 padding，其内部表示不变。codegen 只需要固定偏移的加载、存储和复制。

初步不做以下优化：

- 利用无效位模式的 niche encoding；
- 复用 payload 内部的空闲位存放外层 tag；
- 针对嵌套 enum、dyn 与具体类型组合设计专门编码；
- 为保证所有组合都是两 word 而引入隐含转换。

String 的 inline/heaped 区分可以封装在 String 自身表示中。enum 和 dyn 不应理解或改写 String 内部标签。String 若完整需要 16 字节，外加 tag 是否超过两 word 应由普通布局规则决定，不能预先假定能塞下。

## 七、与执行后端和内存管理的关系

布局表应使字段访问、数组步长、分支读取和已确定函数调用成为机械 lowering。运行时仍需要处理业务检查、外部数据校验、越界和求值循环等依赖实际值的行为。

字节码可以使用 word 槽位；native 后端可以将部分值保存在寄存器中。共同约束是类型表示、调用边界和来源语义，不要求所有后端实际创建相同的 Vec。

内存管理需要与布局一起设计：初始化对象如何发布到 MainWorld、后续 WorkWorld 如何引用不可变对象、slice 如何保持底层对象有效，以及对象如何回收。这里只提出数据表示方向，不改变当前初始化与发布语义，也不预先声称能够消除跨 world 的深复制。

## 八、后续收敛：统一值头部与分类对象表

2026-09-12 补充：首版先采用统一的 `loc + TypeId + data` 表示，暂缓前文的来源分列和静态 TypeId 省略。具体草案见 [RFC 0281](../rfc/0281-uniform-runtime-value-layout.md)。前文保留作为优化方向，不代表首版同时实施。

```text
值：[loc: 12 bytes][TypeId: 4 bytes][data: N words]
```

在这一基础上，heap 按对象类别建立独立的表，而不是让所有对象共用一张通用对象表：

```text
Heap {
    strings: StringTable,
    records: RecordTable,
    dicts:   DictTable,
    arrays:  ArrayTable,
}
```

### HeapId 是表内索引

HeapId 暂定为 u32，仅在所属表内标识对象。相同编号可以同时存在于 StringTable、RecordTable 和 DictTable 中，表示不同对象。裸 HeapId 不足以解释引用，必须配合 TypeId 和所属 world 的上下文。

```text
TypeId → 类型类别 → 选择对象表
HeapId → 表内对象 → 定位存储
TypeId → 具体布局 → 解释内部数据
```

类型类别通过已闭合的类型信息确定，不通过类型名称匹配。静态已知时，codegen 直接生成对应表的访问；只有动态操作才需要读取实际具体类型身份来选择表。

例如 Record 的值携带具体 TypeId 和 RecordTable 内的 HeapId。前者决定字段布局，后者定位记录数据。Array 的 TypeId 确定元素布局，HeapId 定位 ArrayTable 中的底层存储，start/end 决定 slice 范围。

### 各表独立选择存储结构

表本身已经表明对象类别，不必给每个对象再保存通用 kind 标签。也不要求各表采用相同的元素结构，或为每个对象单独进行宿主堆分配。

- StringTable 可以索引连续字节 arena。
- RecordTable 可以索引连续 word 存储，字段按具体类型布局访问。
- ArrayTable 可以管理按元素布局排列的连续存储，多个 slice 共享底层对象。
- DictTable 可以采用专门的哈希索引及键值存储结构。

外层值表示统一，不要求底层对象表示统一。分类表无需为了解释对象重复保存一份通用 LayoutId；通用遍历操作应携带解释对象所需的类型信息。具体表仍可保存必要的存储位置、长度等管理数据。

### 复制、发布与身份

复制和发布的去重键不能只使用 HeapId。单个来源 heap 内至少需要 `(表类别, HeapId)`；若操作跨多个来源 world，还需区分来源 world。具体 TypeId 用于解释对象布局。

同一表内同一对象必须具有一致的底层布局。slice、动态擦除和 trait 访问不能让同一存储被解释成不兼容的结构；动态访问需要保留足够的具体类型信息。

分类表不自动解决 MainWorld/WorkWorld 的引用编码、生命周期或发布重映射。这些规则继续单独收敛，不据此宣称对象发布已经无需复制。

### 尚未决定：RecordTable 是否继续按具体类型细分

当前建议先让所有 Record 共用一个 RecordTable，由 HeapId 定位、具体 TypeId 解释字段，避免为每个 Record 类型创建一张表。这尚未作为确定决策；也可以比较按具体类型分表的分配局部性与管理成本。

## 待收敛的问题

1. 分类表内的存储寻址、HeapId 的 world 身份、容量限制与生命周期规则；RecordTable 是否按具体类型继续细分。
2. String 的具体编码，以及 Tuple、闭包的内联或间接布局。
3. enum 大 payload 的间接存储规则，dyn 的统一宽度与内联容量。
4. 聚合对象的字段来源、数组元素来源及更新传播规则。
5. 各类型的字节大小、对齐与调用 ABI，避免仅凭 word 数量决定布局。
6. 是否由现有 LIR 承担后端无关的执行表示，以及首个后端实验的范围。

后续 RFC 应先收敛这些规则，再用包含标量、String、slice、Record、enum、dyn 转换和来源诊断的纵向样例验证。性能评估应分别观察热数据读取、冷列空间、分配、转换及初始化成本；本讨论不预估收益数字。
