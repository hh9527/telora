# 持久化 Map 首版实测

历史实验记录：PersistentMap 及持久化 Dict 后端已从当前分支删除，本文命令、接口和数据仅用于保留实验结论。

## 范围与口径

独立标准库 `std::map::Map(K,V)`，采用最多 15 个 entry 的持久化 BTree。插入和删除复制路径，共享其余子树。Dict 保持原状。

使用 release 构建，在同一进程中直接调用 Session typed 接口，包含 host 编码和解码，不是 IPC。每项操作顺序测量 20 次，取中位数。初始化包含 `session.initialize` 和首次查询，不包含 Session 加载与引擎模块装载。探测 fuel 为 8,000,000,000，原先 2,000,000,000 不足以构造 2048 个 key；没有修改生产配置。

| key 数 | 编译 ms | 初始化及首查 ms | 查询 ms | 覆盖 ms | 删除 ms | 覆盖分配 B/次 | 删除分配 B/次 | GC 后托管存量 B |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 128 | 64.73 | 57.29 | 0.306 | 0.384 | 0.539 | 1556 | 3776 | 8528 |
| 512 | 59.79 | 318.30 | 0.411 | 0.507 | 0.796 | 1924 | 5652 | 31912 |
| 2048 | 59.66 | 2043.64 | 0.490 | 0.637 | 0.914 | 2484 | 6644 | 125344 |

三个规模的制品均为 1,724,424 B，查询分配均为 76 B/次。托管存量不是进程 RSS，也不包含引擎底噪。规模增加 16 倍时，覆盖操作分配从 1556 B 增至 2484 B，符合路径复制的预期。

首版标准库 BTree 的常数仍较高，2048 个 key 的逐项构造约需 2 秒。`pairs` 递归合并数组，物化最坏为 O(n log n)。尚未做与 Dict 的同口径比较，因此不能据此宣称优于 Dict。

## 验收

- Map 专项测试：6 项通过，1 项手动性能探测默认忽略
- Core 测试：210 项通过
- Wasm 全量测试：171 项通过、1 项失败、1 项忽略
- 唯一失败为 `guest_memory_growth_failure_is_distinct_from_managed_budget_exhaustion`，已在 main `c03dc4fb` 复现相同失败：实际为 managed-budget，而测试期待 allocator-failure
- 随机差分覆盖两组各 520 次操作，检查分裂、借位、合并、根收缩和保留的历史版本
- 验证自定义比较器、来源传播、强制 GC、A/B 固化及两次独立恢复

复现命令：

```sh
cargo test --release -p telora-core
cargo test --release -p telora-wasm persistent_map
cargo test --release -p telora-wasm map_scale_probe -- --ignored --nocapture

```

## RT 核心阶段实测

RT 核心统一执行树算法，编译器提供封闭布局描述。默认比较器在 RT 内执行；标准库保留类型及组合 API。测试仍使用原来的 Int/Int 样本、release 配置和相同调用口径，未更新运行环境二进制或生产配置。

| key 数 | 编译 ms | 逐项初始化及首查 ms | 查询 ms | 覆盖 ms | 删除 ms | 覆盖分配 B/次 | 删除分配 B/次 | GC 后托管存量 B |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 128 | 40.26 | 13.36 | 0.0385 | 0.0764 | 0.0905 | 1884 | 2484 | 8128 |
| 512 | 36.63 | 71.37 | 0.0418 | 0.0850 | 0.1162 | 1876 | 3428 | 31512 |
| 2048 | 36.84 | 734.82 | 0.0446 | 0.0913 | 0.1238 | 2636 | 4188 | 124944 |

制品均为 1,518,342 B，查询分配为 60 B/次。2048 key 下，逐项初始化约快 2.78 倍，查询约快 10.97 倍，覆盖约快 6.98 倍，删除约快 7.39 倍。制品缩小约 12%。覆盖分配从 2484 B 增至 2636 B，约增加 6.1%；删除分配下降，存活托管数据略降。这不是进程 RSS 对比，不代表所有操作的内存都改善。

### 逐项构造的剩余成本

| key 数 | 默认逐项初始化及首查 ms | 默认初始化 GC 次数 | 探测关闭自动 GC 后 ms |
|---|---:|---:|---:|
| 128 | 13.36 | 2 | 10.22 |
| 512 | 71.37 | 15 | 38.02 |
| 2048 | 734.82 | 80 | 163.67 |

关闭自动 GC 仅用于诊断，实验结束仍显式 GC 后测量存活量。没有修改默认 GC 配置。2048 key 的耗时差约 571 ms，说明逐项构造的分配与回收已成为主要优化方向；该差值不是精确的独立 GC 阶段计时。

```sh
TELORA_MAP_PROBE_GC_INTERVAL=0 cargo test --release -p telora-wasm map_scale_probe -- --ignored --nocapture
```

### 批量构造

`from_pairs` 在 RT 内稳定排序、去重后直接建立满足占用率约束的平衡树，保留首 key 代表和末 value，不创建逐项插入的历史版本。

| key 数 | 批量调用中位数 ms |
|---|---:|
| 128 | 0.414 |
| 512 | 4.159 |
| 2048 | 27.767 |

此探测在初始化完成的 Session 中传入倒序排列的 pairs，20 次调用取中位数，包含 host 输入编码、Guest 建树与结果解码，结果为长度。与上表逐项初始化不是相同工作负载，不能直接相除宣称加速倍数，也不能将结果视为纯 RT 建树时间。尚未进行旧版批量接口的同口径测量。

```sh
cargo test --release -p telora-wasm map_bulk_scale_probe -- --ignored --nocapture
```

### RT 阶段验收

- Map 专项 9 项通过，2 项性能探测默认忽略
- Core 210 项、Shared 35 项通过
- Wasm 回归跳过已在 main 复现的内存配额分类失败，其余通过
- 新增批量建树在 0/1/7/15/16/17/31/127/255/256/257/2048 key 边界与 Rust BTreeMap 对照，并在生成树上删除及检查原版本
- 自定义比较器在低 GC 间隔下保持正确，查询、插入、删除和批量构造的比较失败均传播语言诊断
- 原有来源追踪、共享子树、A/B 固化恢复与随机操作验收继续通过

Dict 桥接、默认 GC 策略调整及更紧凑的专用节点布局不在本阶段交付内。首版标准库实现保存在提交 `024e1c5a`，可作为后续对照基线。

## 与 Dict 的同口径对照

使用相同的固定宽度 String key（`k000000` 等）和 Int value，默认 GC，release 模式，20 次 Session 调用取中位数。查询包含 host 参数编码和结果解码；更新返回更新后的 key 查询结果，确保新集合被实际消费。每次更新都基于同一个不可变 base，而不是累计修改。所有调用结果均校验。

Dict 没有独立的插入/删除 API，覆盖和插入使用 `merge(base, from_pairs([(key,value)]))`；删除使用 `pairs → filter(key != target) → from_pairs`。Map 使用 insert/remove。因此删除反映现有 API 完成相同任务的成本，不是两个原生删除实现的算法对照。

| key 数 | 集合 | 查询命中 ms | 覆盖 ms | 插入新 key ms | 删除 ms | 批量构造调用 ms | GC 后托管存量 B | 覆盖分配 B/次 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 128 | dict | 0.0194 | 0.1102 | 0.1257 | 1.2088 | 0.551 | 5376 | 5596 |
| 128 | map | 0.0411 | 0.0990 | 0.0988 | 0.0982 | 0.657 | 9480 | 1092 |
| 512 | dict | 0.0197 | 0.2683 | 0.3369 | 7.5135 | 5.365 | 20736 | 20956 |
| 512 | map | 0.0465 | 0.1131 | 0.1098 | 0.1112 | 5.666 | 36480 | 1372 |
| 2048 | dict | 0.0194 | 2.8291 | 3.1124 | 31.9625 | 22.828 | 82176 | 82396 |
| 2048 | map | 0.0466 | 0.1145 | 0.1110 | 0.1191 | 23.347 | 144384 | 1676 |

批量构造从 host 传入相同的倒序 pairs，返回中间 key 的查询值；计时包含 Rust 输入值复制、host 编码、Guest 构造和结果解码，不能当作纯 RT 建树时间。批量输入 key 唯一；Dict 对重复 key 报错，而 Map 接受覆盖，本探测没有混淆这两种语义。

2048 key 下，Dict 查询约快 2.4 倍；Map 覆盖约快 24.7 倍、新 key 插入约快 28.0 倍，覆盖分配从 82396 B 降至 1676 B。批量构造约为 Dict 22.83 ms、Map 23.35 ms，两者接近。Map 存活托管存量约为 Dict 的 1.76 倍，这不是 RSS。

相同字面量批量初始化及首查：128/512/2048 key 的 Dict 为 3.96/17.72/65.95 ms，Map 为 4.56/17.90/63.05 ms。这里没有逐项插入循环，不能与前面的逐项初始化直接比较。

当前适合的判断：读取为主且一次构造的集合，Dict 的紧凑布局更有优势；需要持久化增量更新的集合，Map 显著减少复制成本。不能据此直接将所有 Dict 替换为 Map。测试输入均为短字符串及 Int value，尚不覆盖大值、长 key 和任意更新分布。

```sh
cargo test --release -p telora-wasm map_dict_comparison_probe -- --ignored --nocapture
```
