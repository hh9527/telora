# Telora 的动机

本文档定义 Telora 稳定的问题陈述和设计动机，回答“为什么需要这门语言”。当前
语言的整体设计见 [`design/LANGUAGE.md`](design/LANGUAGE.md)，共同概念和术语见
[`design/CONCEPT.md`](design/CONCEPT.md)，当前实现架构见
[`design/IMPLEMENTATION.md`](design/IMPLEMENTATION.md)。
文档的权威关系与维护规则见 [`README.md`](README.md)。

RFC 记录单项决策、备选方案与实现证据。它们是设计演进的历史，而不是重新理解
当前设计的首要入口。

## MRT 问题域

Telora 把 **MRT（Modelling、Representation、Transformation，即建模、表示与
转换）**视为一个不可分割的问题域。

### Modelling：建模

一个真实系统所包含的知识远比输入数据的形状更精确：

- 概念以及概念之间的关系；
- 区分有效状态与无效状态的不变量；
- 在多个有效方案中作出选择的策略；
- 由应用提供私有事实的扩展点；
- 判断已有证据是否足以发布结果的规则。

建模决定系统中的数据“意味着什么”，不只是声明字段形状。模型还可能包括可执行
规则、规范化、组合、授权策略以及计划的语义。

这些知识必须留在真正拥有它们的层次。语言提供通用机制；通用标准库提供可复用
计算；领域库提供领域词汇和规则；应用提供自己的事实和策略。实验中的领域概念
不能反向进入无关的标准库或语言运行时。

### Representation：表示

知识必须具有程序、工具、人和 Agent 都能共享的表示。有效的表示不只是一棵可以
序列化的数据树，还应保留：

- 值的类型以及值之间的关系；
- 模块和依赖身份；
- 原始数据、规则和转换结果的来源；
- 可供检查、编辑和确定比较的结构；
- 明确的不确定性，而不是伪造的精确信息；
- Host 在赋予外部意义前可以验证的稳定边界。

表示一旦割裂，同一个概念就会分别出现在配置、schema、校验代码、转换代码、
编辑器元数据和 Host 协议中。这些副本会逐渐漂移，一层中的失败也无法准确解释
另一层中的事实或规则。

因此，Telora 把静态数据、程序值、类型、元数据、诊断和模块接口放进同一个来源
可追踪的语义世界。JSON、TOML 和 YAML 是源码模块，不会在第一道边界就退化为
失去位置的不透明数据。

### Transformation：转换

真实系统不只接受或拒绝一个模型，而是把意图逐步转换为更具体的结果：

```text
意图
  -> 规范化
  -> 根据模型和上下文解析
  -> 在 lowering 过程中验证
  -> 完整、类型化的制品
  -> Host 授权与解释
```

验证与 lowering 往往无法分开。一个意图是否合法，可能取决于某项 capability
能否找到、依赖能否解析，或者完整的目标计划能否构造出来。单独返回 Boolean 的
校验阶段无法忠实表达这种关系。

转换还必须保留证据。规则失败时，诊断应同时指出来自数据或意图的 subject，以及
拒绝它的规则。独立错误应尽可能继续被观察，但证据不完整的候选值绝不能作为成功
制品发布。

## DSL、GPL 与 eDSL

任何 DSL 都必须借助一门通用编程语言（GPL，General-Purpose Language）实现或
承载。DSL 的实现复杂度不会消失：独立 DSL 把复杂度
放进自己的解析器、检查器、解释器、代码生成器和 Host；嵌入式 DSL 则复用承载
语言已有的值、函数、模块、类型和工具链。

因此，评价一门基础语言时，一个关键问题不是它内置了多少领域特性，而是：

> 它能否让领域特征由普通库清楚、可靠地表达，从而形成 eDSL？

好的语言设计应让库拥有领域词汇、规则和 lowering 过程，同时仍能获得静态检查、
来源诊断、模块复用和确定执行。新领域通常应增加库，而不是为每个领域向编译器和
VM 增加特殊语义。

Telora 的具体判断是：**封闭世界假设 + 类型即数据**，可以让较小的语言内核获得
足够好的表达能力和诊断能力。

- 封闭世界使代码、依赖、静态数据和显式输入可枚举，因而可以可靠分析、缓存、
  重放和限制执行。
- 类型即数据使模型表示可以由普通函数构造和解释，从而共同驱动静态检查、运行时
  校验、codec、schema、文档和领域解释器。
- 来源随值和规则流动，使库形式的 eDSL 仍能产生面向领域 subject 的诊断，而不
  只暴露通用库内部错误。

Telora 仍是一门 GPL，但它的通用性集中在封闭、纯粹的数据计算和 MRT，而不是
环境 IO 与任意外部效果。领域 eDSL 建立在它之上；真正的效果始终由 Host 拥有。

## 为什么现有类别仍有缺口

静态配置格式容易检查和交换，但本身不能表达通用复用、策略与转换。Schema 可以
描述可接受的形状，却不能计算目标如何产生。

常见 GPL 提供充分的计算能力，但通常从开放世界出发：环境 IO、动态依赖、效果、
可变状态，以及转换后数据较弱的来源信息。沙箱和 fuel 可以限制破坏，却不会自动
产生权威的语义模型或精确的修复闭环。

专用配置语言通常把某项政策，例如合并或约束合一，设为基础语义。这可以有效，
但每一种专用机制都带来新的组合规则和失败模型。Telora 要验证的是：不可变数据、
普通函数、可编程类型元数据和少量受控桥梁，能覆盖多大范围的 MRT 问题。

Telora 不试图取代所有这些系统。它关注的是这样一块空间：建模已经具有可执行性，
表示必须保持可检查，而转换必须产生可信制品。

## 设计命题

Telora 的核心命题是：

> MRT 可以共享一个较小、封闭、纯粹、确定且来源可追踪的语言模型，而不必把领域
> 政策或外部效果变成语言语义。

这个命题导出四项要求：

1. **通用数据计算。** 函数、不可变值、模块、递归和模式匹配必须足以表达真实的
   建模与 lowering 逻辑。
2. **可编程表示。** 类型是普通代码可以构造和解释的规范元数据，而不是另一门
   schema 语言。
3. **有限且权威的反馈。** 执行和分析都有边界；诊断与语义事实保留来源，也不
   伪造确定性。
4. **明确的权限边界。** Telora 只计算普通值；只有 Host 能观察开放世界，并决定
   输出是否可以产生效果。

Telora 允许递归，而不要求所有程序都能规范化；但每次执行都有确定的 fuel、栈、
调用深度和分配上限。表达能力存在于一个由 Host 控制的有限边界内。

## 价值主张

### 可诊断性是一等诉求

Telora 不把诊断视为语法、类型检查和执行完成后的展示层。对于 MRT 程序，失败能否
解释清楚，与成功能否计算出来同样重要。语言机制从设计开始就必须回答：

- 错误能否同时指向被拒绝的 subject 和施加要求的 rule；
- 来源能否穿过模块、静态数据、普通转换和 TypeMetadata；
- 不完整程序能否保留独立成立的事实；
- 失败是否会产生误导性的连锁错误或部分发布；
- 人和 Agent 能否只根据公开诊断作出局部、可验证的修复。

如果一个功能可以执行，却无法给出稳定、来源准确且与严格语义一致的反馈，那么它
还没有完整进入语言设计。诊断质量不是表达能力的附属指标，而是 Telora 所追求的
表达能力的一部分。

### 简单、平凡胜过魔法

普通数据、普通函数、显式参数、显式返回值和静态模块依赖，是 Telora 首选的构造
方式。领域政策首先应表现为读者可以追踪的程序，而不是隐藏的合并规则、隐式上下文、
编译器特例或无法观察的控制通道。

“平凡”并不表示功能弱，也不表示永远拒绝抽象。它表示机制应当具有较少的特殊规则、
可局部推理，并能复用同一套检查、执行和诊断模型。一个略显冗长但类型关系清楚的
普通库接口，通常优于一个短小却需要编译器猜测意图的接口。只有当重复证据证明这类
冗长来自一般机制缺口时，才应把相应抽象提升到标准库或语言核心。

### 选择性拥抱 PLT

Telora 会使用 PLT（Programming Language Theory，编程语言理论）中的成果，但
不会以类型系统的一般性或理论新颖性作为目标。双向类型检查、rank-1 多态、
TypeMetadata witness、existential boundary、`Never` 和 recoverable semantic fact
之所以有价值，是因为它们改善了 MRT 的表达、诊断或权限边界。

每项 PLT 机制都必须同时计算收益和代价：

- 它是否解决了多个中性、可复现的问题，而不是只优化一个实验；
- 它是否让用户更容易陈述真实关系，并得到更准确的错误；
- 它给语言表面、编译器、VM、工具、文档和用户心智模型增加多少复杂度；
- 普通函数、TypeMetadata、库抽象或 Host 行为是否已经可以忠实解决问题；
- 它是否保持封闭、纯粹、确定、有界和来源可追踪这些不变量。

因此，Telora 既不回避类型理论，也不追求把完整的 PLT 工具箱装进语言。采用某项
机制的理由必须是它以可接受的总成本强化了语言的核心命题。

## 一门 lowering intent 的语言

Telora 是 **a language for lowering intent**。

Intent 是用应用或领域库拥有的词汇表达的高层请求。它不一定来自自然语言，也不是
Telora 的特权语法类别；它是普通的类型化数据和代码。

库根据模型、规则和显式上下文解析意图。成功计算会产生完整制品，例如 build plan、
process plan、deployment object、migration、生成源码树或 query plan。制品仍然
只是普通数据，拥有它并不等于拥有执行权限。

三项责任必须分离：

```text
应用或 Agent          编写 intent
Telora 库             验证并 lowering intent
Host                   授权并解释 artifact
```

语言不内置 build、deployment、analytics、ontology 或 Agent action。这些领域通常
应增加领域库和狭窄的 Host adapter，而不是 VM 指令或通用标准库概念。

## 一门 harness agent 的语言

Telora 也是 **a language to harness agents**。

Agent 可以高效地产生模型、程序和意图，但“能够生成”并不能证明正确性、权限或
可追责性。Prompt 约束和输出 schema 可以塑造回答，却不能建立一个可执行的语义
边界。

Telora 允许 Host 把生成结果放入受控闭环：

```text
有限上下文 + Agent 生成的 intent 或程序
  -> 在封闭世界中解析、分析和执行
  -> 来源可追踪的诊断，或完整的类型化制品
  -> review、修复、比较、签名或拒绝
  -> 可选的 Host 授权效果
```

“Harness”不表示增加 Agent 专用语法，也不表示让语言自己调用模型。它表示让生成
结果可检查、可重放、可诊断，并且在明确的 Host 边界接受之前不具备外部权限。

同样的性质也服务于人编写的程序。Agent 是对语言设计的高强度检验，不是另一种
语义模式。

## 边界

Telora 不以成为以下系统为目标：

- 通用的有副作用应用语言；
- 单独成立的操作系统安全沙箱；
- 定理证明器或全函数语言；
- 通用 workflow、action 或 Agent 协议；
- 把领域概念放进核心的 ontology 语言；
- 隐藏的代码生成器或无限制宏系统；
- 为每个应用领域积累编译器特例的框架。

外部 IO、时间、持久化、重试、权限、事务和效果执行属于 Host。领域意义属于领域
库和应用。实验可以发现缺失的通用机制，但必须先用中性的语言概念陈述这些机制，
才能进入核心或通用标准库。

## 评价标准

以下现象说明项目正在沿正确方向推进：

- 非平凡 MRT 策略可以写成普通的类型化 Telora 程序；
- 同一表示可以驱动检查、校验、转换、工具和 Host 协议验证；
- 诊断可以跨来源连接 authored subject、转换值与拒绝规则；
- lowering 只有在证据完整时才发布制品；
- 每次执行都在配置边界内得到值或结构化失败；
- 不完整程序保留独立事实，但不假装知道更多信息；
- 新领域主要增加 eDSL、普通库和狭窄 Host adapter；
- Agent 可以只依据公开诊断修复结果，而不获得隐藏实现知识或外部权限。

如果新领域反复要求 VM 特例，类型级行为必须在隐藏语言中重复实现，转换值丢失
来源，或者生成代码能够绕过 Host 发布边界，就需要重新审视这套设计。
