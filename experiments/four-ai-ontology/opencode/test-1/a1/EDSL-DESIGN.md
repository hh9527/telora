# Ontology eDSL 设计规范

这是一个"嵌入式领域特定语言"（EDSL）的设计规范。它定义**方法论**与**契约**，
但不规定具体函数签名、模块布局、路径算法或教学结构——实现者（你）选择表面 API。

目标是：两个结构不同的企业，能用同一套 eDSL 定义各自的"本体"（度量、维度、
关系、粒度、物理映射），并让共享库承担全部的行业级验证与降级编排；企业只表达
自己知道的私有知识。

## 分层

```text
eDSL 库（你实现）
    类型构造器、capability 协议、编译/路径/发布规则
企业模型（未来的使用者）
    封闭的 Entity/Measure/Dimension/Filter 类型
    关系事实、度量公式、物理映射、企业策略
    最终计划构建
```

eDSL 库**不得包含**任何企业概念（实体名、表名、SQL 片段、度量公式、状态码）。
企业模型**不得复制**行业级编排（能力查找、独立降级、完整性、路径闭包、分类、
诊断、原子发布）。

## 定义角色（TypeMetadata families）

eDSL 提供可执行的 TypeMetadata 构造函数（普通函数，接受 `TypeOf(...)` 参数，
返回结构类型记录），用于定义企业的"语义角色"：

- **MeasureDefinition**：一个度量的身份、语义值类型、自然粒度实体、聚合分类、
  以及 `Fn(Id, Input) -> Option(Output)` 形式的降级函数。
- **DimensionDefinition**：一个维度的身份 + 模型特定的降级函数。某些维度会派生
  多个需求或在需求存在前就拒绝，因此所需实体应放在输出的载荷里。
- **RelationDefinition**：关系的语义端点（from/to 实体）和基数分类，外加一个
  模型特定的物理映射载荷。库知道"一条关系在基数规则下连接两个实体"，但不知道
  表名、列、连接表达式。

这些构造器生成的记录，其**字段语义**由库定义（身份、自然粒度、聚合、lowerer、
端点、基数、映射），但**具体类型参数**由模型提供。两个企业的物理映射可以结构
不同——共享的是"语义角色"，不是"载荷形状"。

## Capability 编译

eDSL 提供一条类型化的编译协议：

```text
请求的身份数组
  -> 独立执行每个 capability（缺失定义则产生带来源的诊断）
  -> 保留原始结果（Option 数组）+ 完成值数组
  -> 发布证据：仅当每个请求都有值时，才允许发布
```

关键契约：

- **独立执行**：一个 capability 失败不短路其他 capability；独立错误要能一次收集
  （供 Host 恢复）。
- **来源保持**：降级回调必须收到"请求的原始身份"，使产物的来源指向意图，
  而不是模型目录里的定义。
- **发布原子性**：完整性证据未满足时，不发布任何计划。证据应携带"哪些值完成"
  的信息，而不是一个孤立的 Bool。
- **所需节点汇聚**：从完成的度量/维度输出中提取关系需求，应是一条共享规则，
  通过类型化选择器工作。

## 路径分类与验证

eDSL 提供关系路径的分类与验证规则：

- 输入：安全关系目录、fan-out 关系目录、基准节点、目标节点、端点选择器。
- 输出（作为三个结果一起派生）：安全连接边、仅能通过 fan-out 到达的目标、
  两个目录都无法到达的目标。
- 验证规则：对每个需求，若其目标处于 fan-out 或 missing 集合，则报告一条
  带**模型主体**（而非泛化 Node）的诊断。
- 完整可达性由共享规则计算，合并安全与 fan-out 两组边；catalog 的语义必须
  干净——同一条边不应同时出现在两个分类里。

## 分析管线（企业不复制编排）

共享库维护一条有序的编译管线，供企业模型调用：

```text
独立降级能力
-> 组合可用度量片段（企业策略回调）
-> 派生关系需求
-> 分类安全/fan-out/缺失路径
-> 运行下游独立诊断（在发布门之前）
-> 仅在完整证据时发布，并调用企业的最终计划构建器
```

- "运行诊断先于发布门"：即使能力/路径证据不完整，也要运行候选构建器以收集
  独立诊断，然后丢弃其值——不能用一个过早的发布门隐藏无关错误。
- 度量组合与最终计划构建是**真正的企业策略**，作为回调由企业提供。
- 其余（查找、降级、收集、完整性、闭包、分类、诊断、发布）全部由共享库承担。

## 企业扩展点（企业必须提供的）

一个企业模型需要提供：

1. 封闭的 Entity/Measure/Dimension/Filter 与计划类型；
2. 度量与维度的 capability 数组（具体 lower 函数）；
3. 安全与 fan-out 关系事实（带物理映射载荷）；
4. 度量组合策略（返回一个类型化组合度量）；
5. 身份/lowerer/所需节点/诊断主体的类型化适配器；
6. 其他阶段（如过滤）产生的额外所需节点；
7. 最终构建器：把验证过的语义输入降级为企业的物理计划。

它**不需要**重写：能力查找、独立降级、部分结果收集、编译完整性、所需节点
组合、图闭包、路径分类、维度路径诊断、原子发布门。

## 诊断契约

- 诊断必须保留三层来源：**意图**（请求的身份）、**模型事实**（关系/能力定义）、
  **共享规则**（eDSL 中的检查位置）。
- 缺失能力、粒度扩张（fan-out）、缺失路径、未授权实体，都要有可识别的、
  指向模型主体的诊断。
- 不要为了继续执行而构造假的计划或跳过独立检查。

## 原子发布

- 只有"每个请求能力都产生了值 + 路径验证通过 + 企业构建器成功"时，才发布
  一个完整的、类型化的执行计划。
- 发布的计划是惰性产物（如 SQL 语句、结果模式、渲染绑定），不是执行授权。

## 实现自由度

- 表面 API、模块布局、函数命名由你决定。
- 路径算法可以有界（例如固定轮数的闭包），但必须诚实标注这个界限。
- 可以使用 typed 选择器/回调来保持类型精确；**不要**用 `Any`、`Dyn` 或
  String 身份来掩盖类型关系。
- 最终交付物应包括：库实现、一份教"企业模型作者"的教程（EDSL_TUTORIAL.md）、
  一份契约清单（AI3_CONTRACT.md：企业必须定义什么 / eDSL 保证什么）、
  以及一份设计说明（STAGE2_NOTES.md：你做的表面选择与理由）。
