# RFC 0293：与 EOL 无关的紧凑来源坐标

- 状态：实施中
- 日期：2026-09-14
- 前置：RFC 0291、0292

## 决策

运行时 Loc 保持 96 bit：来源 ID 为 u16，起止位置各为 u40。
每个位置由高 16 bit 的行号和低 24 bit 的行内 UTF-8 字节偏移构成。
行号、行内偏移从 0 开始，范围采用 `[start, end)`。
CRLF、LF、单独 CR 均为一次换行。CRLF 内部的字节边界映射到前一行末尾，
不产生额外可表达的逻辑边界。

来源 ID 0 留给没有来源的运行时值；可注册 ID 为 1..65535。
每个来源最多 65536 行，每行内容最多 16777215 个 UTF-8 字节，
以便行末的排他边界也可表示。超限在注册输入时报告错误，不截断、不回绕。

## 物理表示与边界

运行时以三个小端 u32 承载 Loc：

```
word0 = source | ((start >> 32) << 16) | ((end >> 32) << 24)
word1 = start 的低 32 bit
word2 = end 的低 32 bit
point = (line << 24) | utf8_column
```

Loc 加上 TypeId 仍是 16 字节的值头。GC、诊断捕获等消费者必须从
word0 低 16 bit 获取来源 ID，不能再将 word0 整体当作 ID。
Wasm ABI 升为 14，不保留旧位置 ABI 的兼容路径。

前端的 SourceDatabase/解析器仍使用原始字节范围进行切片和编辑器交互。
源码注册时建立仅供编译器/Host 使用的行首和行末索引，生成指令、debug site、
函数名称以及数据注入/打包时转换到紧凑坐标。数据计划共享其来源索引，
不复制数据树。制品的来源表只保存 ID 和名称，不再保存 bols。

Host 可直接解码行号与 UTF-8 列。若需截取原始文本或转换为 UTF-16/终端宽度，
由 Host 利用原始文本索引处理。特权 `std/_rt.SourceRange` 的 start/end
是上述 40 bit 位置整数，不再是文件绝对字节偏移。

JavaScript 的 Number 可精确表达 53 bit 整数，足以承载 40 bit 位置；
位运算仅用于单个 u32，跨 word 使用乘法和加法组合，不对完整位置做
JavaScript 的 32 bit 位运算，也不把任意 u64 当作 Number。

## 确定性范围与验证

当换行仅改变源码空白或数据文件的格式空白时，位置编码和来源表不再引入
制品差异。字符串内容不做隐式 EOL 替换，多行字符串的值语义不因此改变。

验证覆盖：最大来源/行号/行内偏移、跨 256 行的高位拼接、容量溢出、
Unicode 字节列、混合换行及 CRLF 内部边界、三种 EOL 的相同源码制品、
数据位置、运行时诊断、GC 来源保留以及 JavaScript 最大值解码。
