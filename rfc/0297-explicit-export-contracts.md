# RFC 0297：顶层值的显式完整类型契约

状态：草案；顶层值要求完整类型、私有顶层声明同样要求完整签名的方向已确认，具体规则待评审。
关联：[#193](https://github.com/hh9527/telora/issues/193)、RFC 0296。
实验分支：`fix/193-directional-fit`。

## 动机与范围

模块接口应由声明确定，而不是由哪个使用者先提供推导证据决定。显式顶层契约使全图
类型求解能够区分接口的检查依据与实现内部的推导变量，也使错误程序中的健康类型信息
更容易保留，便于诊断和 LSP。

所有普通顶层值具有显式、完整的类型契约，无论是否导出。局部变量、函数体内闭包
仍允许现有推导；泛型调用的类型实参仍可省略。不改变 Fn 表面语法，不增加推导期
求值，也不按模块隔离或重跑求解。此前只检查导出值的范围由本规则替代。

这项语言规则不能单独修复 #193：其 increment 复现已经有完整签名，仍被错误调用
污染。显式契约与不污染契约的约束实现必须配合落地。

## 用户可见规则

### 普通顶层值

源码模块中，模块顶层的普通 def/let 绑定必须在该绑定的声明处提供完整类型注解。
常量、容器、函数、类型元数据值均适用，不因初始化表达式容易推导而例外。

```telora
export def answer: Int = 42;
export def increment: Fn(Int) -> Int = fn(value) { value + 1 };
export def identity: for(T) Fn(T) -> T = fn(value) { value };

# 拒绝：接口类型依赖初始化表达式的推导。
export def missing = 42;
export def inferred_function = fn(value) { value + 1 };

# 私有顶层同样要求签名；函数体内的局部绑定仍可推导。
def private_answer: Int = 42;
def local_inference: Fn() -> Int = fn() { let answer = 42; answer };
```

函数声明外层的完整类型已经覆盖参数和返回类型，不要求在 fn 表达式中重复书写。
反过来，仅在 fn 初始化表达式内部写参数/返回注解，不替代绑定声明上的顶层契约。
已有配对的 `decl name: Type; def name = ...;` 使用 decl 上的完整签名，
无需在 def 重复；这是已有声明语法，不引入新语法。

`export {name}`、改名导出只改变可见性。契约检查直接枚举模块顶层声明，
不依赖导出表反向筛选，因此先私有定义、再导出不会改变签名要求。

```telora
def internal: Fn(Int) -> Int = fn(value) { value };
export {internal};

def other = 42;  # 拒绝：即使不导出，也缺少顶层签名。
export {other};
```

普通值别名也是新绑定：`export def alias = internal` 仍需给 alias 写类型，不能沿
initializer 追溯原声明来绕过规则。它与符号重导出不同，沿用 RFC 0296 的边界。

### 什么叫完整

完整不是“没有泛型”，而是契约中的类型仅依赖已 resolve 的类型身份及显式绑定的
类型参数，不依赖初始化表达式、调用实参或其他值使用处来补齐接口空槽。

- `for(T) Fn(T) -> T` 完整；T 在契约中显式绑定，不是 Unknown。无约束的 T 本身合法。
- 泛型参数的显式 bounds 必须完整解析；不从函数体或调用者自动补出隐含的导出 bounds。
- 原本用于推导的 `_` 等省略形式不得在顶层契约中留下自由类型变量。
- 显式类型别名、名义类型及类型层面的构造应用可使用；其自由参数必须全部得到绑定。
- 函数契约必须包含参数和返回类型。类型别名包装的函数契约也按同一规则验证。
- 不能仅凭最终得到 Known 就算完整：靠 initializer 或消费者填完的接口仍违反规则。
- 用于契约的类型定义本身出错或未解析时，保留原始诊断，不伪装成合法契约，也不重复
  报“缺少签名”。

显式写成 Dyn 或其他现有宽类型，是用户选择的完整契约；不允许编译器为缺失注解
自动补 Dyn。类型语法中与推导 hole 不同的既有特殊类型含义不因本 RFC 改变。

### 重导出与其他导出身份

| 导出对象 | 契约来源 |
| --- | --- |
| 本模块普通 def/let，包括后来经 export 列表导出的绑定 | 该绑定的显式完整注解 |
| 从其他模块导入后直接重导出的普通值符号 | resolve 链终点的原声明契约，无需重复注解 |
| 类型声明及类型别名 | 类型声明的现有语义；不属于普通值绑定 |
| enum variant、newtype 构造器等类型域身份的直接导出 | 类型定义决定的签名/身份，沿用 RFC 0296 |
| native 声明 | 既有显式 native 契约，不能从 native 名称猜测 |
| namespace 重导出 | 所指模块的导出表，不新增值推导接口 |
| JSON/YAML/TOML 等数据模块 | 既有 Host/模块协议提供的 `{data: Value}` 契约 |

重导出不新增执行或推导步骤，不把普通值赋值视为符号重导出。遇到 Unresolved 或
Conflicted 的 resolve 结果，消费原阶段结论，不在类型阶段重新搜索名字。

不为顶层模式绑定新增语法。若已有模式绑定形式可以用于顶层，其显式整体注解必须
足以仅通过类型骨架的静态解构确定每个绑定符号的契约；不能用初始化值填接口空槽。
无法满足时应要求改为有显式注解的普通顶层绑定，不能静默豁免。

### entry、检查与未使用导出

entry、测试入口和普通库导出遵守同一规则；不按符号名字、文件位置或 CLI 命令豁免。
编译器/测试工具生成的源码模块也必须生成合法签名，而不是给生成代码开兼容通道。

只要源码模块进入当前解析和求解图，就检查其所有顶层契约，包括没有被调用的导出。
未加载的模块不因此强制加载。未实例化模板按绑定参数下的契约检查，不能强迫它成为
一个具体运行时值。可执行闭包仍按入口需求选择，并在 seal 前完成具体实例类型闭合。

`check --only-types` 在静态阶段执行相同检查；不创建 VM、不求值数据或 property
来确定顶层契约。其他执行命令不能绕过该静态检查。

## 全图 MIR 语义

1. 全图符号 resolve 闭合后，根据模块顶层作用域及符号身份确定需要检查的原声明；每个声明
   只建立一次契约记录，多个导出名/重导出引用同一身份。
2. 独立求解顶层注解和其类型依赖，确认骨架、绑定参数和 bounds。允许模块间类型
   引用及既有合法递归类型；不靠执行函数体或用户代码取得契约。
3. 在 MIR 中保留声明契约、对应来源和完整性结论。用该契约检查 initializer/函数体，
   使用处也消费同一契约；泛型调用只为当前实例分配必要推导槽。
4. 所有顶层声明的实现与局部绑定仍在同一张图上推导。它们可以消费顶层契约，但不能通过
   值证据替未完成的顶层注解确定接口类型。
5. 接口类型确定与声明实现合法是两件事。函数体或调用违反契约时记录失败约束，
   保留契约类型及健康部分的信息；session 仍不能 seal 或进入求值阶段。

这是全图内部的依赖和证据边界，不要求逐模块发布接口，不要求复制环境或每个模块
执行一遍求解器。成功规范化后的 TypeId 继续由后续 codegen 机械消费。

模板声明的 SymbolId 标识函数族，导出和重导出传递该身份与显式契约，而不是传递
所有调用者共同填充的实例槽。每个值域引用独立分配实例化参数槽，闭合后再以声明身份
和确定的类型实参选择具体实例。相同实参可以复用实例代码，但不能合并尚未完成的
调用约束。错误使用只记录该处失败，不反向污染模板契约及其他使用处。

例如 `foo: for(T) Fn(T) -> T`，`foo(foo(a))` 的两处引用独立实例化，但由该签名可知
两者最终具有相同 T；其他上下文中的 foo 可以形成不同实例。这个区分与 enum variant
从类型域物化到值域的边界一致；来源记录仍按 RFC 0296 的具体规则处理。

普通值绑定不会重新泛化：局部 `let foo = foo;` 的右侧引用模板并产生一次实例化，
左侧 foo 遮蔽模板名，后续引用共享这个函数值的同一组类型实参槽。可以由局部后续
使用补齐实参，但 seal 前必须确定；不能让一次调用选择 Int，另一次调用选择 String。
独立引用模板声明与重复引用已经物化的函数值必须根据 resolve 身份区分，不能根据
相同的名字或沿值别名追溯模板而再次实例化。

没有显式签名的顶层声明不能因后续恰好推导成功而被当成合法契约发布；MIR 可以保留
额外的实现推导信息用于诊断，但必须与已验证的声明契约区别表达。不能只检查有没有
诊断文本：缺失或不完整契约也应作为 MIR 中的未满足义务阻止 seal。

## 诊断

- 缺失签名：primary 指向普通顶层值声明，明确要求顶层值提供完整类型；
  不因声明私有或另经列表导出而改变诊断。
- 不完整签名：primary 指向注解中需要值证据才能填补的位置；区分未绑定参数、
  推导 hole 和已存在的类型解析错误。
- 实现或调用失配：使用 #192 的中立文案，保留失配使用位置及契约来源。不能因为
  已知接口仍存在就忽略实现错误，也不能通过把共享接口标为 Conflicted 来识别错误。
- 多个错误导出继续收集独立诊断。多个别名重导出同一错误声明，不重复制造根因。

## 迁移与实施

这是破坏性语言变更，没有 warning-only 过渡模式或关闭检查的兼容参数。

先提交本 RFC，再在当前实验分支推进：

1. 盘点 std、CLI/Host 生成模块、语言测试及文档示例中的普通顶层值，区分显式契约、
   缺失注解和依赖推导 hole 的注解。盘点作为迁移工作量依据，不用数量推测已完成。
2. 实现基于 SymbolId 的顶层契约记录、完整性检查及 seal 条件，先以独立语言用例
   验证注解与重导出语义。
3. 将 #193 的失败约束记录与契约记录关联，恢复精确上下文并保留健康类型结果。
   实验原型仍需审计未知变量和各个 Fit 入口，不能直接宣布已经符合本 RFC。
4. 迁移仓库内普通顶层、生成器和测试入口；正例补齐契约，诊断负例避免因新增的
   缺失签名错误遮住其原本测试的行为。原始复现需标明对应的历史版本语义。
5. 同步 `docs/` 与语言指南，完成回归后记录 release 性能。ontology 等外部使用者
   先列出迁移影响；跨仓库修改按对应任务授权推进，不给它们设置编译器特例。

## 验收

- [ ] 普通标量、容器、函数、元数据值的无注解顶层声明均拒绝；完整注解对应正例成功。
- [ ] 私有顶层与导出顶层同样要求签名；局部推导保持可用，改变导出可见性不改变契约要求。
- [ ] 直接导出、export 列表、改名、多层重导出、普通值别名分别覆盖，不以语法绕过。
- [ ] 显式泛型及 bounds 合法；调用实参继续推导；未调用模板不被强制具体化。
- [ ] 不完整接口即使能从 initializer 或调用者推导也拒绝；合法类型别名和绑定参数
  不被当作 Unknown；类型域及数据模块按各自明确契约处理。
- [ ] 共享有签名函数的一次错误调用不改变其接口或健康调用的类型；两个独立错误
  分别报告，错误实现也拒绝；这些结果不依赖模块清单、导入或使用顺序。
- [ ] 静态检查继续产生独立诊断，健康信息可查询；删除诊断文本后，缺失契约或失败
  约束仍阻止 seal。类型阶段不执行用户代码。
- [ ] 仓库内 std、生成源码、测试和当前文档完成迁移；无按模块名、入口名或测试
  路径豁免，无基于初始化表达式猜测顶层契约的兼容路径。
- [ ] 以独立 `.telora` fixtures 覆盖语言规则，少量 Rust 测试验证 MIR/诊断/seal；
  完整回归通过，并记录相同语料迁移前后的 release 纯类型与完整检查耗时。

## 延后或不采用

- 仅检查导出绑定：已由所有顶层普通值统一要求签名的规则替代。
- 通过消费者或函数体推导顶层签名：保留了本 RFC 要消除的接口反向依赖。
- 普通值别名、字面量或测试入口自动豁免：使契约边界依赖初始化形式或使用场景。
- 外部签名文件、新函数语法、自动生成并永久采纳推导签名：不是实现此规则的前提。
- 为修复诊断而拆成多 session：违背全图求解方向，也不解决单模块内的共享契约污染。
