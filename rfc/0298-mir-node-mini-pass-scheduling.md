# RFC 0298：以 MIR 节点 mini pass 驱动静态求解

状态：实施中。
跟踪：[#199](https://github.com/hh9527/telora/issues/199)。
关联：[#197](https://github.com/hh9527/telora/issues/197)、
[#165](https://github.com/hh9527/telora/issues/165)。

## 动机与范围

#197 已将源码转换改为 CST 直接 lowering 到扁平 HIR，移除了完全 Owned AST。
但是，扁平的数据结构和全图求解并不意味着调用栈深度与输入无关。
符号索引、引用链解析、类型匹配和已解析类型的替换仍有递归调用：父操作调用子操作，
等待返回后继续。深表达式、长的无环引用链和深层类型都可能增加 Rust 调用栈深度。

本 RFC 改变的是递归调度过程。MIR 可以包含递归关系；这些关系不应要求编译器
使用同样深度的调用栈来处理。

范围是 module-resolve、symbol-resolve、type-resolve 及其闭合所需的辅助处理。
保留三个阶段的职责与边界，不将它们混为一个可任意交错的求解过程。
不修改语言语法、解析器恢复策略、运行时或 Wasm codegen。
不宣称因此解决解析器及整个编译器的所有栈深度问题。

## 核心模型

ctx 的主体就是进行中的 MIR。所有需要跨任务保留的语义输入、待填槽位、
中间结论和最终结果都由 MIR 的节点或关联表承载，不另建一份平行的求解图。

queue 中的任务在逻辑上是：

```text
Task = (MirNodeId, MiniPassKind)
```

一个 mini pass 对一个 MIR 节点进行局部处理。它读取已有事实，把新结论填回 MIR，
并登记后续需要处理的任务，然后返回外层调度循环。它不能递归执行另一个 mini pass。

这里的节点包括模块、符号、表达式和类型求解操作等实体，不限定为源码表达式。
实现可继续使用现有的强类型 ID 和分阶段任务枚举，不要求新增统一 Node 大枚举。
同一源码节点的不同泛型实例或替换上下文必须有独立的操作身份，不能仅以源码 ID
去重。相应上下文通过 MIR 中的 ID 关联，不复制作用域或整份类型环境。

ctx 除 MIR 外只需维护队列、等待关系、入队标记等调度信息。
短期局部变量可以留在 mini pass 内；跨任务等待的结果必须有可定位的 MIR 槽位。
辅助扫描可以用局部显式工作表，不能隐藏依赖输入深度的递归调用。

## 调度与填空

每次处理产生以下效果之一：

- 已有信息足够：填充或精确化结果，通知依赖该信息的任务。
- 仍需其他信息：登记所依赖的槽位，确保相应生产任务已被调度，然后返回。
- 已有证据冲突：记录冲突结论及其诊断证据，继续处理其他节点。
- 结论没有变化：不重复唤醒消费者。

例如，替换 `Array(T)` 的类型参数时，MIR 中记录原类型、替换上下文、子结果槽位
和输出槽位。mini pass 先安排子类型的替换，待子结果可用后再构造并归一化
`Array(child)`。父任务等待的是 MIR 槽位，不是 Rust 函数返回值。

等待登记必须与当前事实的读取协调，不能遗漏已经发生的更新。
任务入队需去重；重新运行只由相关事实变化或明确的阶段收尾动作触发。
不能把条件不足的任务立即反复放回队尾，形成无进展轮询。

queue 表示显式工作表，不强制所有操作使用 FIFO。简单遍历可使用 `Vec<Task>`，
依赖求解可使用待执行队列与等待表。FIFO 本身不保证子任务早于父任务完成，
正确性必须建立在依赖就绪条件上，而不是任务碰巧出队的顺序上。

## 阶段结束、错误与收敛

队列耗尽表示当前没有可推进的任务，不自动表示求解成功。
此时根据阶段规则检查剩余槽位及依赖关系：保留无法解析的引用、无法确定的类型，
识别需要诊断的环，并生成已有语义要求的诊断。

暂时等待不是最终 Unresolved。实现应区分内部调度状态与阶段对外的结论。
冲突产生时保留双方证据并报告一次；结束时汇总剩余未解项，避免给同一根因
反复追加级联诊断。符号冲突仍区分重复定义与被引用时发生的星号导入歧义。

symbol-resolve 即使存在 Unresolved/Conflicted，也将其结论交给 type-resolve。
后者不得重新按名字解析，也不得猜测一个替代绑定。类型阶段同样保留 Unknown
和 Conflicted；存在阻止闭合的结果时不得 seal 或进入求值。

信息更新遵循现有约束语义，只在实际新增证据或精确化结论时产生推进。
任务队列不是收敛性证明：无限生成泛型实例等问题继续由现有展开收敛分析处理，
不以任务数量上限代替语义判断。本 RFC 不加强现有保守分析的证明能力。

## 确定性与可观察性

稳定 ID 的分配使用确定的模块、源码及实例身份规则，不依赖任务偶然完成的顺序。
内部临时 ID 如需归一化，在 seal 前完成；对外可观察的 ID 必须保持全量构建确定性。
有效程序的绑定、类型和实例集合不应由合法的任务调度顺序改变。

诊断在证据产生处记录，展示时按稳定的来源及诊断身份排序、去重。
不要求错误程序中采用不同冲突发现次序时的临时代理结构逐项相同，但不能因先处理
哪个消费者而污染已声明的类型契约。

阶段性 debug 应能从 MIR 看出节点已有结论、尚缺的槽位，以及关联的等待原因。
不要求新增公开 CLI 参数，也不把完整调度历史长期保存在 MIR 中。
静态阶段依旧不持有 VM、不执行 .telora 代码；后续阶段直接消费封闭结果。

## 实施计划

1. 改造 symbol-resolve 的索引及引用闭合。用节点任务与 ScopeId 保留词法语义，
   将导入、重导出、别名和命名空间依赖移交显式调度，删除被替代的递归路径。
2. 改造 type-resolve 中剩余的递归处理，包括类型匹配、已解析类型替换、参数出现
   检查和模式检查；复用已有迭代式约束求解，不另建一套通用执行框架。
3. 审视 module-resolve 到 MIR seal 的调用链，覆盖间接递归以及辅助遍历；
   完成整体测试与性能观察后，将已落实的模型写入设计文档。

每一步直接替换目标处理路径，不保留递归兼容入口。已有迭代实现无需为了形式一致
而全部重写。实现使用正常 Rust 模块，不用 `include!()` 或 `#[path]` 拆文件。

## 验收条件

- 对同一语义输入，现有绑定、类型、实例物化、错误分类和来源位置保持正确；
  缺失或冲突节点不阻止其他独立节点得到结论。
- 分别覆盖深 HIR 表达式、长无环符号引用链、深类型匹配和替换，在较小线程栈上
  完成对应 MIR 处理。测试可直接构建扁平输入，避免先被解析器栈深度限制拦住。
  #197 的 lowering 小栈测试不能替代这些测试。
- 引用环和无法推进的依赖能结束并给出阶段结论；无变化任务不反复入队。
- 重复全量构建的 sealed ID 和诊断输出稳定；对具备多个就绪节点的代表性图，
  调整合法调度顺序后检查语义结果一致。
- 运行完整测试及 lab-ontology 的真实用例。语言行为优先用运行时读取的独立
  `.telora` 用例覆盖；小栈和调度器不变量保留必要的 Rust 测试，不用 `include_str!()`。
- 对比本 RFC 实施前同机 release 的纯类型检查与完整检查，记录时间和峰值 RSS。
  目标是无明显回退，不预设队列化必然加速；若发现回退，定位任务数量、重复唤醒
  或等待表开销后再决定调整。

## 备选方案与边界

扩大线程栈只能移动故障边界，不能获得与输入深度无关的调用栈。
仅扁平化数据结构不能消除递归调度；把所有操作改为整图反复扫描则容易增加无效工作。
独立的 continuation 结果树会重复 MIR 已有的填空职责，因此不采用。

暂不引入并行任务、通用异步执行器、持久化调度状态或增量编译协议。
调度模型可以为后续工作提供基础，但这些都不是本次验收条件。
