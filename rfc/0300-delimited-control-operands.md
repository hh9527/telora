# RFC 0300：控制表达式操作数的显式边界

状态：已接受，实施中。
关联：[#165](https://github.com/hh9527/telora/issues/165)。
分支：`fix/165-parser-stack-safety`。

## 动机与范围

定界符预检能够限制括号、分支体和函数体的嵌套，但 `if if if …` 在第一个
左花括号出现前就已经递归进入多个条件。类似问题也存在于 `match match …`、
`return return …`。只禁止相邻的两个 if 不够，`if !if …` 同样会产生递归。

本 RFC 采纳讨论中的语法收口：控制表达式的操作数里，嵌套控制表达式必须有显式
定界符。无需承诺支持任意深的无括号控制表达式，也不为它增加另一项可配置深度配额。

## 用户可见语义

在 if 条件、if-let 的被匹配值、match 的被匹配值、return 的返回值，以及 fn
的显式返回类型注解中，if、match、return、fn 表达式不能在同一定界符层直接开始。
这一约束跨越一元和二元运算符，不能通过 `!`、`+` 等绕过。

需要将控制表达式嵌入这些操作数时，用括号标出子表达式边界：

```telora
# 拒绝：未限定边界的嵌套控制表达式。
if if True { True } else { False } { 1 } else { 0 }
if !if True { True } else { False } { 1 } else { 0 }
match if enabled { Some(1) } else { None } { _ => 0 }

# 接受：显式括号建立边界。
if (if True { True } else { False }) { 1 } else { 0 }
if !(if True { True } else { False }) { 1 } else { 0 }
match (if enabled { Some(1) } else { None }) { _ => 0 }
return (if enabled { 1 } else { 0 });
```

已有的调用参数、索引、数组、插值、块及闭包体本身就有定界符，不要求额外再套
一层括号。正常 `if … { … } else if … { … } else { … }` 不是条件操作数的
嵌套，继续支持。模板函数、Fn 类型语法、运算符结合性和所有值的类型语义不变。

诊断指向需要加括号的控制关键字，并说明应建立显式子表达式边界。超深的带括号
输入由既有定界符预检拒绝，不能进入递归 parser。

## 内部语义

词法 token 决定定界符边界；字符串和注释里的字符不参与。解析器在进入上述
操作数时记录边界，遇到控制表达式时检查是否仍处于同一边界。正常退出操作数时
恢复外层状态。节点仍按原有 CST 形状构建，HIR/MIR 无需增加新的表达式类型。

这一检查须在开始解析内层控制表达式之前执行，不能先构造深树再做语义验证。
错误输入也不得绕过边界或导致无限恢复；发现此错误可以终止当前模块的语法分析，
但须保留来源位置及可消费的错误结果。

## 备选方案

- 只检查相邻关键字：不能覆盖一元前缀或混合控制关键字，弃用。
- 为这些写法增加通用递归深度配额：本轮优先采用清晰的语法边界，不额外保留此路径。
- 任意表达式都改为显式调度 parser：成本较高，不是本 RFC 的前提。

## 实施与验收

1. 实现操作数边界检查，保持 CST 形状、结合性和源码位置。
2. 用独立 `.telora` 用例验证合法写法与明确的语法诊断；已有无括号用例补齐括号。
3. 在独立子进程的 1 MiB 栈线程上覆盖长 if/match/return 混合前缀、运算符绕过、
   合法括号及畸形输入。超限或语法不合法必须正常诊断，不可栈溢出。
4. 复核生成 parser 的递归环：剩余环须跨受限的定界符边界，或已使用循环。
5. 更新正式语言文档并通过核心及语言验收。JSON/YAML/TOML 的保护仍由 #165 跟踪，
   不因本 RFC 完成而提前宣布整个 issue 完成。
