# RFC 0316：由 Service 初始化结果驱动的运行期制品

- 状态：Draft，等待设计提交与审阅
- 跟踪：[#248](https://github.com/hh9527/telora/issues/248)
- 日期：2026-10-24
- 基线：`754471f2`；依赖 RFC 0305、0307、0309、0315
- 实验分支：`explore/snapshot-specialization`

## 动机与范围

Service 的初始化负责把声明、输入源和配置转换为运行期可消费的状态。普通 snapshot 已经固化这份状态，但仍携带求得它的生成代码。运行期读取 Ready demand 时，即便立即返回准备结果，引擎仍可能加载或延迟编译整个初始化函数。

本 RFC 将同一程序的连续构建表达为：

```text
M → 生成 A → 执行 A → A.result
M + A.result → 生成 B
```

M 是同一份已封闭程序。A 是 Service 的准备和初始化计算；程序可以自行将模型自检放入 A。A.result 包含准备结果及其运行期行为依赖。B 是消费本次 A.result 的运行期制品。

Telora 只认识 Service、初始化、类型、闭包、函数依赖和制品，不认识 ontology、Entity、Dataset 或 transform/lowering 等领域概念。

范围包括正式构建接口、跨阶段值与身份、运行期根、Ready demand 替换、失败及资源语义、回归验收。后续生成优化在同一 issue 下跟踪，不以扩大本次语义范围为前提。

## 已有实验依据

实验对同一源码使用同一二进制顺序构建普通 snapshot 和 B。文件大小采用十进制 MB。

| 模型 | 普通 snapshot | B | 减少 |
| --- | --- | --- | --- |
| 5 Dataset 规模样本 | 10.73 MB | 8.44 MB | 21.35% |
| 20 Dataset 规模样本 | 12.22 MB | 8.66 MB | 29.13% |
| 40 Dataset 规模样本 | 14.21 MB | 8.96 MB | 36.97% |
| IC 50 Dataset | 43.42 MB | 11.52 MB | 73.46% |

四者保留的生成函数体均为 2,634 个，含 895 个 Ready getter。该数量排除保留原槽位的 trap stub。IC 的 code section 从 37.18 MB 降至 6.74 MB，运行期 snapshot 从 3.19 MB 降至 1.74 MB；静态 data section 仍为 2.99 MB。

IC 各变体启动 3 个独立进程，冷启动分项合计中位数为 962.73 ms → 378.26 ms，进程内第三次请求为 12.08 ms → 10.81 ms。普通 snapshot 与 B 的领域验收均通过，包括 50 Dataset 投影 SQL 的 SQLite 执行、过滤、聚合、Latest、GraphPair、GraphUnion 和错误输入拒绝。该结果是本方案的使用方验证，不成为语言层特例或默认测试依赖。

完整 A 的生成与执行仍然存在。IC 总构建单次为 15.77 s → 15.49 s，其中准备计算仍约 4.3 s；不能据此承诺构建提速。

## 用户可见接口

```sh
# 初始化并发布运行期专门化制品
telora build @src/lib --snapshot -o app.wasm

# 保留完整初始化状态与代码的 snapshot，用于对照及诊断
telora build @src/lib --snapshot=full -o full.wasm

# 显式选择与 --snapshot 相同的模式
telora build @src/lib --snapshot=runtime -o runtime.wasm
```

不带 `--snapshot` 的制品继续由宿主在启动时初始化。`--source NAME=SOURCE` 在 snapshot 模式中由构建过程消费；初始化结果固化后，宿主沿用现有 snapshot 来源覆盖限制。

实验选项 `--specialize-snapshot` 不作为长期公共接口。实现迁移其本地脚本及测试，正式接口以 `--snapshot[=runtime|full]` 为准。

这是构建优化，不要求用户改写 Service 或声明新的 A/B 语法。B 的独立运行只需要现有 `telora-run`，不需要源码工作区或编译器。

## 可信边界与类型身份

整个过程在一次构建内连续完成。M、类型世界、函数表和 A.result 不经过用户编辑或外部缓存回灌。可信性由构建生命周期保证，不增加签名、模型指纹匹配或重复自检协议。

编译器应以内部类型及生命周期绑定 Service 编译结果和准备结果。调用方获得的是本次构建的封闭能力，不能通过公开的 `(bytes, snapshot, roots)` 任意组合接口拼接不同构建。

跨阶段值使用已有类型化 snapshot 表达能力，包括普通值、名义类型值、共享对象、有环环境、闭包、Type/TypeOf、来源和可恢复资源。闭包的代码依赖必须一并保留；宿主不解释或执行语言函数。TypeId 的含义来自同一已封闭类型世界，不能重新类型检查 M 或压缩后独立编号再消费旧结果。

首版保持 TypeId、函数表槽位、静态 demand 地址与类型布局。移除函数体不等于重排函数表。允许保留 trap stub；编号压缩是后续优化，必须同时证明所有引用均被修正。

## 运行期状态根与代码根

运行期根至少包含：

- 已初始化的 Service handler、集合路由与捕获环境
- 每次请求所需的输入 materializer、codec、构造检查和诊断路径
- 上述函数可达的全局值、Property 结果、来源和资源恢复描述
- 这些值中闭包的函数依赖，以及这些函数继续读取的状态

初始化入口、source 注入暂存值和不再可达的声明计算不自动成为 B 的根。普通 full snapshot 保留原有完整初始化行为和根集合。

值遍历使用封闭物理布局，不通过扫描任意整数猜测 TypeId、地址或函数表槽位。代码依赖必须覆盖普通函数、生成 codec、静态数据模块、函数指针、间接调用和封闭环境。首版可以复用链接 relocation 的精确边；若移至更早层次，必须保留同等覆盖能力，不能仅依赖较粗的源码函数图。

Service handler 的值图不包含请求 materializer 的所有代码身份，因此编译器必须将这些 ABI 回调显式作为代码根。不能只扫描 handler 的表面字段。

## Ready demand 的阶段替换

读取 Ready demand 在 B 中依赖其已准备的值，不再依赖求值过程。B 将读取替换为满足原调用 ABI 的 getter，并在此停止沿初始化代码向外保留依赖。

getter 保持原 caller-owned 输出约定、完整值头、名义类型身份和共享引用。需要输出缓冲时复制正确宽度；无输出缓冲时返回已保活的值。getter 不重新执行 provider、初始化、自检或配置解析。

遍历 Ready 值中的闭包时，继续保留闭包的代码和状态依赖。未 Ready 的 demand 不能伪装为已完成；若它是合法运行期依赖，应保留其求值代码及所需状态。无法证明依赖闭合时采用保守保留或明确构建失败，不能发布可能访问已删除状态的 B。

B 仍对每次请求执行输入解析、输入 codec、构造检查、权限及业务拒绝逻辑。A 对模型或配置的验证不能被解释为对未来输入的验证。

## 初始化行为与失败语义

本 RFC 不提前改变 A 的求值规则。初始化期间执行哪些 Property provider、如何加载 data/source、如何报告初始化诊断，与 full snapshot 使用相同的保守路径。provider 的副作用或失败不能因为 B 不再需要该 provider 的代码而被跳过。

A 失败、超出配额、来源不匹配、snapshot 导出失败或 B 无法闭合时，构建不发布新制品，已有输出文件保持完整。原子发布在全部步骤成功之后发生。

准备结果捕获不改变仍存活的 A 实例：临时 packing 完成后恢复原有根坐标和运行期状态。根、Ready 状态和闭包集合应通过同一次类型化导出返回给构建器，不依赖可被后续导出覆盖的 RT 全局缓存，不要求 Host 解析 Guest snapshot 的私有字节前缀。

B 的正常请求、GC、reset 和 trap 后重建均沿用现有资源预算。重建恢复 B 的准备结果，不执行已删除的 A 计算。错误输入、构造检查失败和配额耗尽必须保留可诊断行为。

## 构建组织与度量

正式实现将实验中的接口收敛为以下内部阶段：

1. 封闭 M，建立 Service 编译计划和确定的类型、函数身份
2. 生成并加载 A，消费构建 source，完成准备和初始化
3. 捕获本次 RuntimePublication，包含 snapshot 及封闭的行为依赖
4. 以准备结果替换 Ready 读取，闭合 B 的代码和数据依赖
5. 验证 B、附加准备结果并原子发布

初始化状态、代码根和 Ready demand 摘要作为内部对象流动，不通过正式制品中的 tooling 自定义段形成可外部回灌的协议。最终制品继续剔除编译器 tooling 数据。

阶段计时采用 Service 与编译抽象。现有 `service_prepare`、`service_initialize`、`service_seal`、`snapshot` 保留，专门化子阶段位于 snapshot 之下。仅在请求计时或用量诊断时输出结构化计时与专门化统计；统计区分保留函数体、getter、stub、代码字节和准备结果字节，避免把槽位保留误报为函数索引压缩。

## 将裁剪提前的边界

当前流水线只有一次完整代码生成；B 通过本次代码与结果派生。仅将 B 裁剪从最终 Wasm 移到更早的 IR，并不会自动省掉 A 所需的完整生成成本。

后续在同一 issue 下分别研究：

- B 计划提前：在封闭的代码生成计划中表达 PreparedRead、运行期根和依赖收缩，减少 B 派生时的字节解析和中间数据
- A 范围收缩：分析初始化实际需要的执行闭包，区分“创建一个运行期函数值”和“初始化时调用该函数”，明确间接调用的保守边界
- Property evidence：记录静态 required/optional 证据能否减少初始化闭包；存在开放属性查询时保守回退
- 生成成本：定位前端、实例化、代码生成、链接和初始化的成本，按真实瓶颈选择优化位置

A 的范围收缩若改变 provider 是否执行，必须单独明确其可观察语义，不能随 B 专门化暗改。前端类型检查不会因为 B 不需要某段生成代码而自动跳过。每个优化都以与 full 模式的行为对照和分阶段度量作为依据。

## 延后与备选方案

- 最终 Wasm 独立裁剪工具：缺少同次构建的准备结果与封闭类型依赖，不作为正式公共接口
- 把 A.result 限制成 JSON：无法直接承载已有闭包、名义类型与类型身份，首版复用类型化 snapshot
- 对单个 True 作完成证明：不能替代实际准备结果，也不能消除求得该结果的代码依赖
- 跨构建缓存 A.result：会增加来源一致性和身份重映射契约，当前不提供
- 任意用户入口 A/B、通用编译期执行语法、World 或 AutoTrait 新语法：不在本次 Service 构建能力范围内
- 单独为领域模型定制构建器：会把领域概念引入 Telora，采用统一 Service 流程

## 实施计划

一个 issue 跟踪所有阶段，不按阶段拆分 issue。

1. 单独提交并审阅本 RFC，保留实验结果及基线
2. 正式化编译计划与 RuntimePublication，将 RT 导出改为一次性完整结果，去掉 Host 私有 snapshot 解析和未绑定的公共专门化参数
3. 接入正式 snapshot 模式、结构化统计、指南和回归，保留 full 对照模式
4. 在生成样本上定位可提前的边界，先消除重复元数据解析，再逐项评估 A 的执行闭包收缩
5. 以真实使用方验收和阶段耗时确认收益，再由人单独授权合入

## 可执行验收条件

- full 与 runtime 两种 snapshot 在同一源码、source 和请求上给出一致响应及输入诊断
- 覆盖 Type 身份、名义类型、共享与有环闭包、静态 data 模块、外部 source、生成 codec 与构造检查
- 覆盖未调用但被捕获的函数、高阶间接调用、Property required/optional、未 Ready 依赖及保守回退
- 正常请求、强制 GC、重复请求、fuel/memory trap 后恢复均能运行 B，不重做 A
- A 失败和 B 构建失败不覆盖既有输出；最终制品不带 tooling 根信息或可外部回灌的阶段协议
- 不修改模型源码即可复现 5／20／40 规模样本及 IC 的现有 transform 验收；不要求知识发现验收
- 前移优化分别报告完整构建、A 生成/加载/执行、B 派生与冷启动，不以体积下降代替构建提速证据
